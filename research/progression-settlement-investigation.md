# Settlement and reload regression investigation — 2026-09-06

**Current result: SAVE_VERSION 6 implements the authorized simulation identity
protocol; all 28 settlement regressions pass.** The protocol-limit and proposal
sections below are historical evidence, superseded by the final
“Authorized simulation follow-up regression gate” section. Their references to
an out-of-scope simulation file or failing delayed probe are not current limits.

Scope: progression accounting and persistence. No economic constants changed.
The executable instrument is `node tools/checkprogression-settlement.mjs`.
It imports the production progression factory, deterministic contract generator,
game-state factory and event bus. Its only persistence substitute is a Map-backed
implementation of browser localStorage. One compatibility case imports the actual
drill simulation, advances its real fixed steps and uses its public debug depth
seam to reach completion; real start, score, result payload and event code run.
It is a lifecycle test, not a drilling-rate or UI test.

## Historical protocol limit, before the authorized simulation follow-up

The current `src/sim/drilling.js` start and completion messages identify a contract,
but do not carry an immutable acceptance/run identity or a hole sequence token.
`S.contract` is the same contract reference passed to `startHole()`. A legitimate
second hole can have exactly the same completion values as the first. Therefore
a delayed old completion delivered *after a new matching DRILL_START* cannot be
reliably distinguished from the new hole through the present public payload.
Payload fingerprints would reject legitimate identical holes. A complete protocol
solution requires a token published by the simulation at start and completion,
persisted and consumed by progression; that production file is outside this task.
The separate executable probe
`node tools/checkprogression-settlement.mjs --probe-delayed-completion` captures
an actual simulation completion, starts the next hole, then delivers the captured
old event. It exits nonzero while that old event can pay the new hole. It runs
independently of the ordinary settlement gate so this documented cross-file gap
cannot be mistaken for successful coverage of the protocol.

This limitation does not excuse ordinary immediate replay or save/reload replay:
the regression gate requires those to leave money, XP, reputation, wear, ledger,
run counters and active-job/site state unchanged.

## Original token protocol proposal

Production ownership required: `src/game/progression.js` plus
`src/sim/drilling.js`. This is a proposal, not an implemented guarantee.

1. **Progression owns two persisted counters.** Allocate a distinct `runId` on
   every successful acceptance, including repeat rescue postings with the same
   contract ID. Persist the next run sequence and active `runId`. Persist an
   active run's `attemptId`, incremented for *every simulation start*, including
   retries of an unfinished hole. `holesDone + 1` is insufficient: an aborted
   attempt and its replacement otherwise have the same identity.
2. **Sim obtains a snapshot from progression before starting work.** Add a
   synchronous `beginHole(contract)` API that validates the active contract,
   increments the attempt counter, arms `holePending`, marks dirty and returns
   an immutable `{ runId, attemptId }` value. `startHole()` stores those scalar
   values on its own new-run state, then emits them as top-level fields of
   `DRILL_START`. The main context already exposes `ctx.progression`; no new
   shell call site is necessary for the normal sim path. Issuing the token
   through a return value avoids reliance on listener registration order.
3. **Complete publishes the captured values.** The simulation's `complete()`
   adds those two stored scalars to `HOLE_COMPLETE`; it must not read token
   properties back from mutable `state.contract` or `S.contract` at completion.
   Old payloads must retain their old values after the next start.
4. **Progression validates and consumes before side effects.** Require active
   contract, matching `runId`, matching `attemptId` and `holePending`. Consume
   the eligibility in the same atomic operation as all accounting. A replay
   after another start has an older attempt; a replay after explicit reaccept
   has an older run; an immediate replay has no pending eligibility.
5. **Reload and reset have defined identity behavior.** Save both IDs and the
   pending flag with the accumulator. Reload keeps them; restarting the physical
   simulation through `startHole()` issues a newer attempt before work. Preserve
   the allocator's in-memory high-water mark across reset so a late pre-reset
   event cannot collide with newly accepted work in that same page. The allocator
   is bookkeeping: no wall-clock or random economic constant is needed. Legacy
   saves gain IDs through migration; their next real start issues a fresh token.

Do not silently accept tokenless completions for a run once a token has been
issued: that would bypass the new guard. The no-sim demo and main QA completion
bridge are currently tokenless; either route them through the same API in a
separate scoped follow-up or keep any explicitly limited compatibility mode
clearly separated from the strict sim path. Production consumers should treat
`DRILL_START` as notification, not a way to invent or reset payment identity.

Required token regressions: retain all ordinary cases; make
`--probe-delayed-completion` pass; add same-contract abort/restart replay,
same-rescue-ID reaccept replay, active reload/restart replay and reset/reaccept
replay using captured real simulation payloads. The ordinary simulation case and
protocol probe both pass the real `ctx.progression` reference to the sim, matching
the application's context rather than a standalone sim-only setup.

## Authorized simulation follow-up regression gate

The simulation file is now authorized to the separate simulation agent. This
test owner changed only the settlement executable and this note. The old
`--probe-delayed-completion` command is now an alias of the ordinary gate; the
delayed-completion test always runs, so it cannot be hidden by a successful
ordinary run. The original 19 cases remain in the gate.

The new cases use actual `createDrillSim()` starts, fixed steps, scoring and
completion emission. A small bus boundary can hold only `HOLE_COMPLETE`
delivery; it neither synthesizes a result nor implements accounting. Stale
delivery asserts deep equality of the entire shared game state as well as the
serialized run accumulator. Replacement results must increase the real hole
count by exactly one and reject another delivery of the same actual payload.

Coverage added: next-hole delayed replay; actual active abort/restart; queued
completion after abandon and explicit same-ID reaccept; completed rescue run
followed by reload and same-posting reaccept; pending physical attempt reload;
reset and same-ID reaccept; immutable `beginHole()` identity and completion's
captured identity despite a newer allocator attempt; synchronous completion
listener starting the next hole plus microtask replay; trailing completion stop
retaining the old identity; and the unpaid QA preview boundary.

The root's final reload policy deliberately tightens step 5 of the historical
proposal above: a physical pending attempt is invalidated when loaded because
the physical simulation does not resume from the saved drilling depth. The
career accumulator survives, and a real subsequent `startHole()` allocates a
new attempt. The regression requires a pre-reload physical completion to be
rejected both immediately after load and after a real restart. Tokenless legacy
save compatibility is tested independently by the retained original cases.

This CPU gate does not measure penetration rates, rendering, UI interaction or
GPU performance. Advancing depth through the simulation's published QA seam
isolates lifecycle and settlement behavior without changing physics or rates.

Verified against the owner's `SAVE_VERSION = 6` implementation: **28/28 cases
pass, exit 0**. The former failing delayed real-simulation probe now keeps money
4469, one hole and one ledger entry unchanged after the next start. Queued stale
results after abort/restart, abandon/reaccept, reload and reset/reaccept keep
money 4500, zero holes and zero ledger entries unchanged. An old rescue result
after reload and explicit reaccept preserves money 5190, three holes, one
completed contract and three ledger entries. Replacement physical attempts
settle once; duplicate replacement events leave all shared state unchanged.

The immutable capture assertion passes even when `beginHole()` allocates another
attempt while the older simulator is active: its eventual result still contains
the original start's IDs and cannot claim the newer eligibility. A synchronous
completion listener that immediately starts the next simulation also leaves the
completed attempt's trailing `DRILL_STOP` identity intact; a microtask replay of
its result cannot pay the next hole.

Existing rescue-contract metadata diagnostics (`archetype` and `flushMedium`)
remain visible in the test summary. They do not cause a settlement failure and
were not repaired by inventing data or changing unrelated production files.

The unpaid-preview case additionally replays its actual explicit-null-ID result
immediately after same-ID acceptance, before the first physical `beginHole()`.
It leaves all shared state and the new run unchanged, then the real simulation
starts and settles once. This closes the boundary where a preview's null fields
could otherwise be mistaken for an older tokenless completion payload.
